1. What Tickets is (and isn't)

Tickets is a personal lane board. You drive it in the browser, and Claude drives it over MCP. Both share one SQLite file (tickets.db), and every card records who did what.

It sits next to JIRA and similar trackers, not in place of them. Team work, planning with others and anything shared stays there. Tickets is for the local loop: you hand coding tasks to an agent on your machine and review what comes back.

Local and single-person only. It is one process, bound to 127.0.0.1. It has no auth, no accounts and no sync: the person at the board is logged as "User"; agents log under their own names. Never put it on a network, never host it online and never share it with a group.

2. Run it

You need Python 3.12 or newer and uv. Chrome too, but only for the browser tests.

Start the server:

uv run uvicorn app:app --host 127.0.0.1 --port 8123 --log-config log-config.json

Give Claude Code the board's tools:

claude mcp add --transport http tickets http://127.0.0.1:8123/mcp

8123 is the port the repo's scripts use. Any other free port works, but it is not a runtime setting: change restart-backend.ps1 and the claude mcp add URL to match.

Then open the board and create a project under "projects…". There is no default project, and a card needs one.

3. The board

Lanes

todo → plan → develop → test → verify → done

todo
Your backlog: not started. Move a card on to plan to start it.
plan
The agent writes a plan and any open questions.
develop
The agent builds it, following the plan and your answers.
test
The agent reviews the changes and runs the tests, fixing what it can. The review is Claude Code's own /code-review on the card's branch, plus a check against the card's request, plan, answers and checklist.
verify
The agent is done: you check the result.
done
Finished: nothing more happens to it.

So todo is yours, plan, develop and test are the agent's, and verify and done are yours again.

The header

  • project tabs: All shows every project's cards; a project's tab, marked with its color, shows only that project's. Under All each card carries its project's name in its color. The board remembers the tab you picked. With many projects the tabs scroll sideways.
  • projects…: each project's name, path (the absolute folder of its git repo, where the agent works), agent instructions (how to build, test and deploy, and how to install dependencies in a fresh worktree) and color. "delete project…" moves its cards to "No Project", where agents never work. Adding a project opens a todo card for each thing its setup still lacks — a path, or rules saying how to test or deploy. Fix it, then archive the card. The best home for a project's rules is the CLAUDE.md in its repo, which every Claude Code session reads anyway; it counts for these cards just like the instructions, which then only need what is specific to the board, such as the deploy target. "merge into the base branch" or "open a pull request" picks how a card that passed its tests lands.
  • show archived: shows the archived cards instead.
  • New Card: opens a draft. Nothing is saved until you close it. The draft starts in the project of the tab you are on, or the first project under All; the project picker under the title changes it.

Cards

  • Drag a card to another lane, or up and down inside its own column to reorder it: a column is a queue, and an agent takes the top card of it. Dropping anywhere on the page puts it in the nearest column. A card an agent moves lands at the bottom of the lane it arrives in.
  • Click a card to open its sheet. Every field saves as soon as you leave it, so there is no save button; "close", or a click on the board around the sheet, closes it. The sheet holds the description, the plan, the open questions and your answers, the checklist, labels, links (parent and blocks), the activity log, comments and "archive". Cards are never deleted, only archived. The log leaves out what the dots, the session button and the pull request link already show, and an agent taking or dropping a card itself.
  • A card the agent has worked shows "session" and the start of its id under the title: click it to copy claude --resume <id>, which reopens that run's Claude Code session in a terminal. A card that landed by pull request also links to it there.
  • An agent's comment has a "claude's output" box under it, closed: open it to read the whole run as you would have seen it in the terminal — every file it read, every command it ran, and what it cost.
  • A card in verify also has a "move to done" button in its sheet, next to "close": the one click that ends the card.
  • Ctrl- (or ⌘-) click toggles a card in the selection; shift-click takes the whole run from there to the card, as long as both are in the same lane. Dragging one card of a selection moves all of them; dragging an unselected card moves it alone. A plain click clears the selection and opens the card, and Esc clears it.
  • The done lane has "archive all" for every done card the board shows; one card is archived from its sheet.

Signals

A card leads with up to three dots, on the board and in its sheet. Each shows only while it is lit; a card with none of them has no dot.

  • green dot: it pulses while an agent is working on the card.
  • blue dot: the card's branch is on the project's base branch, set by the agent's deploy step. purple dot: it is deployed to the local test backend or a device, lit by the agent's deployed: comment. Moving the card back to plan, develop or test clears them.
  • red stripe down a card's left edge, with a "blocked by #12" pill: the card is blocked, it can't start until those cards are done. amber stripe, with a "blocks #37" pill: other cards wait for this one. A card that is both has a half red, half amber stripe and both pills. The other card can be in another project. A link to or from a done card no longer counts, and done cards are never marked; the marks update by themselves when a blocker moves to done.
  • ⟶ arrows go from a blocking card to the cards it blocks, across lanes or within one. They are faint so a busy board stays readable: hover a card to light its arrows, both ways. An arrow shows only when the board shows both cards; one in another project's tab, archived or done has just the pill. Arrows never get in the way: clicks and drags go through to the card below.
  • status bar, at the bottom: which agent is working on which card, doing what, and since when. Click a card in it to open it.

4. The agent

Nothing works the board by itself. You start the work by hand: open a Claude Code session in the project's folder and run /tickets-start: it works the board every 15 minutes while that session is open (/tickets-start once for one run, /tickets-start 12 for card 12 only). A tick with nothing to do costs no tokens: a hook that /tickets-start installs answers it with tickets: nothing to do (<time>) before the model wakes, and lets it through when a card is ready, the board is down or the folder has no project. If the board is down it starts it, and if the session has no board tools (Claude Code connects them only when a session starts, so a session opened before the board has none until /mcp reconnects) it works over the board's web API instead. /tickets-start can start the board when you log in, so that rarely happens. It works every ready card of that project in plan, develop and test through to verify, and writes what it does onto the board as claude-agent: the plan, comments, the moves, and a new idea card for any follow-up it finds. Cards in "No Project" are never worked. It works up to 3 cards at once, but only one in test at a time. Each stage of a card (plan, develop, test) starts a new background agent with a clean context, handed the whole card: its description, plan, answers, checklist and comments, and the project's rules. Tests, the deploy and the merge into the base branch go one card after another. The status bar shows the card it started last and how many are in flight. A card that passes its tests is pushed as card/<id> and then lands the project's way: merged locally into the base branch, or opened as a pull request with gh, whose merge the next run notices and marks with the blue dot.

5. How you work with it

  1. Create a project under "projects…". Point its path at a git repo, put its test and deploy rules in the repo's CLAUDE.md and anything board-specific in its agent instructions. Whatever you leave out shows up as a card in todo telling you what is still missing. Or let /tickets-start do it: run in a Claude Code session in the repo's folder, it starts the board if it is down, checks the MCP server , helps write the CLAUDE.md rules and creates the project, fixing only what is missing. Then it works the board every 15 minutes (or /tickets-start 10m) for as long as that session stays open, and ends with a link to the board; /tickets-stop stops it. /tickets-open-board opens the board in your browser any time.
  2. New Card in todo: a title and a clear description of what you want and why.
  3. Drag it to plan, and the next run of /tickets-start takes it. Watch the status bar and the comments. The plan's steps become the card's checklist and the agent ticks each one as it finishes it, so the checklist (and the ☑ done/total chip on the board card) is its live task list.
  4. Open questions in the plan? Fill in "your answers": the next run replans with them. A question that comes with options shows them as radio buttons under the questions, the agent's pick marked "recommended": a click writes N. <option> into your answers, and you can still type there.
  5. In verify: read the comments, look at the branch, try the deployed build. Then merge card/<id> yourself and move the card to done. A project whose deploy instructions do the merge leaves you only the last one.
  • Not what you asked for? Rewrite the description, move the card back to plan; the next run takes it again.
  • Keep one concern per card, keep project instructions current, use links for dependencies, and archive what you no longer need.

6. Other agents over MCP

Any MCP client can use the board at http://127.0.0.1:8123/mcp. The tools: list_cards, get_card, create_card, update_card, comment, link_cards, unlink_cards, create_user, list_projects and set_activity.

  • Every write passes actor, the caller's name, so the log says who did what.
  • Plans go in plan, never over the person's description.

7. Limits

  • No auth, no multiple users, no remote access.
  • No live push: the board checks every few seconds and refreshes itself when anything changes.
  • No search and no attachments.
  • Cards are never deleted, only archived.
