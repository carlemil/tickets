A card at a glance

Click a card on the board and its sheet opens. Here is one with every field filled in; a new card, or one the agent has not planned yet, shows fewer. The board has the details.

  1. Number and dots: the card's number, led by its signals: green while an agent works on it, blue once it is merged into the base branch, purple once it is deployed (see signals).
  2. Title: what needs doing, in a line.
  3. archive: takes the card off the board. Nothing is ever deleted; "show archived" brings it back.
  4. move to done: only in verify: you have checked the result, and one click ends the card.
  5. close: closes the sheet. Every field saves as you leave it, so there is no save button.
  6. Who and when: who created the card and when; once an agent has worked it, "session" (click to copy claude --resume <id>), and a "pull request" link when it landed by one.
  7. project: the repo the card belongs to, and so the folder the agent works in.
  8. description: your request: what you want and why. The agent never writes over it.
  9. activity: everything that happened to the card and who did it, with the comments. Older lines fold away behind "show N earlier"; an agent's comment has a "claude's output" box with its whole run.
  10. say something: a comment, logged with your name; ctrl+enter sends it. A new card has neither this nor the activity until it is created.
  11. plan: the agent's plan, written in plan. Its steps become the checklist. Hidden until the agent writes one.
  12. open questions: what the agent needs you to decide before it builds. A question with options gets a row of radio buttons below it, the agent's pick marked "recommended". Hidden while there are none.
  13. your answers: your replies to the questions; a radio click writes one here. The next run replans with them. Shown once there are questions.
  14. assignee: who has the card: you, or an agent while it works. A card assigned to a person is never taken by an agent.
  15. lane: the stage it is in, the same as dragging it to another column.
  16. labels: free tags, comma separated.
  17. checklist: steps to tick off. The agent ticks its plan's steps as it finishes them, and the board card shows done/total.
  18. links: this card's parent, and the cards it blocks. A blocked card waits until its blockers reach verify or done.

1. What Tickets is (and isn't)

Tickets is a personal lane board. You drive it in the browser, and Claude drives it over MCP. Both share one SQLite file (tickets.db), and every card records who did what.

It sits next to JIRA and similar trackers, not in place of them. Team work, planning with others and anything shared stays there. Tickets is for the local loop: you hand coding tasks to an agent on your machine and review what comes back.

Local and single-person only. It is one process, bound to 127.0.0.1 unless you host it on your LAN. It has no auth, no accounts and no sync: the person at the board is logged as "User"; agents log under their own names. Never host it online and never share it with a group.

2. Run it

You need Python 3.12 or newer, uv, git and the Claude Code CLI (claude). Chrome too, but only for the browser tests.

  1. In the Tickets repo, install the dependencies with uv sync.
  2. Start the server: 
    uv run uvicorn app:app --host 127.0.0.1 --port 8123 --log-config log-config.json
    On Windows, powershell -NoProfile -File restart-backend.ps1 starts or restarts it in the background.
  3. Link the three skill folders (skill-start, skill-open-board, skill-stop) into ~/.claude/skills as tickets-start, tickets-open-board and tickets-stop, once; the README shows the commands. They are links, so a change to a skill reaches every session.
  4. Open a Claude Code session in the folder of the repo you want worked and run /tickets-start. It does the rest, fixing only what is missing: it offers to start the board at every logon, installs the idle gate, registers the board's MCP server, writes the repo's CLAUDE.md test and deploy rules with you, creates the project, and then works the board (see the agent).

The idle gate is a UserPromptSubmit hook in ~/.claude/settings.json (skill-start/idle_gate.py): when a loop tick finds no card a run would take, it answers "nothing to do" before the model wakes, so an idle tick costs no tokens. It needs a system python on PATH; without one /tickets-start says so and skips it, and idle ticks still work, just not for free.

Without /tickets-start, give Claude Code the board's tools by hand, at user scope so every project's sessions see them:

claude mcp add --scope user --transport http tickets http://127.0.0.1:8123/mcp

Then open the board and create a project under "projects…". There is no default project, and a card needs one.

8123 is the port the repo's scripts use. Any other free port works, but it is not a runtime setting: restart-backend.ps1, the claude mcp add URL, the skills and skill-start/idle_gate.py all name it, so change them to match.

On your LAN

To open the board from another device on your network (a laptop, a phone), click settings… in the header and tick host the board on the LAN. The backend then listens on every address (0.0.0.0) instead of 127.0.0.1 only. Changing it needs a backend restart, and the board does that itself: it runs restart-backend.ps1, the sheet shows "restarting…" for a few seconds, then lists the address(es) to open from the other device, such as http://192.168.1.20:8123/; the first one is the likeliest, the others are often virtual adapters (WSL, Hyper-V). Only the backend restart-backend.ps1 runs (port 8123, this folder, Windows) restarts itself; one started some other way (another port, uvicorn without --host, not Windows) cannot: the sheet says how to apply the change, and it applies the next time you start it with restart-backend.ps1. If the board cannot come up on the LAN address, the restart falls back to this computer only (see restart-backend.log) rather than leave you without a board. Untick it to go back to this computer only; a device that opened the board over the LAN loses it then, and the sheet there says so.

  • There is no password. Anyone on the same network can read and change every card. Use it at home or on a network you trust, never on public Wi-Fi.
  • The setting lives in settings.json beside tickets.db, which restart-backend.ps1 reads on every start, logon start included.
  • This computer keeps using http://127.0.0.1:8123, so the agents, the MCP registration and the skills need no change. The MCP endpoint (/mcp) still answers only this computer; other devices get the board, not the agent tools.
  • Windows firewall. The first time the board listens on the LAN, Windows may ask whether to allow Python on networks: allow it on private networks. If you missed the prompt, or your network is marked public, other devices cannot connect; set the network to private, or add an inbound rule for TCP 8123 from an administrator PowerShell: 
    New-NetFirewallRule -DisplayName "Tickets board" -Direction Inbound -Protocol TCP -LocalPort 8123 -Action Allow -Profile Private

3. The board

Lanes

todo → plan → develop → test → verify → done

todo
Your backlog: not started. Move a card on to plan to start it.
plan
The agent writes a plan and any open questions.
develop
The agent builds it, following the plan and your answers.
test
The agent reviews the changes and runs the tests, fixing what it can. The review is Claude Code's own /code-review on the card's branch, plus a check against the card's request, plan, answers and checklist.
verify
The agent is done: you check the result.
done
Finished: nothing more happens to it.

So todo is yours, plan, develop and test are the agent's, and verify and done are yours again.

The header

  • project tabs: All shows every project's cards; a project's tab, marked with its color, shows only that project's. Under All each card carries its project's name in its color. The board remembers the tab you picked. With many projects the tabs scroll sideways.
  • projects…: each project's name, path (the absolute folder of its git repo, where the agent works), agent instructions (how to build, test and deploy, and how to install dependencies in a fresh worktree) and color. "delete project…" moves its cards to "No Project", where agents never work. Adding a project opens a todo card for each thing its setup still lacks — a path, or rules saying how to test or deploy. Fix it, then archive the card. The best home for a project's rules is the CLAUDE.md in its repo, which every Claude Code session reads anyway; it counts for these cards just like the instructions, which then only need what is specific to the board, such as the deploy target. "merge into the base branch" or "open a pull request" picks how a card that passed its tests lands.
  • settings…: settings for the whole board. For now one: host the board on the LAN, so other devices on your network can open it (see On your LAN).
  • show archived: shows the archived cards instead.
  • docs: opens this manual in a new tab.
  • New Card: opens a draft. Nothing is saved until you close it. The draft starts in the project of the tab you are on, or the first project under All; the project picker under the title changes it. A draft has no activity log or comment box: comments come once the card exists.

Cards

  • Drag a card to another lane, or up and down inside its own column to reorder it: a column is a queue, and an agent takes the top card of it. Dropping anywhere on the page puts it in the nearest column. A card an agent moves lands at the bottom of the lane it arrives in.
  • Click a card to open its sheet. Every field saves as soon as you leave it, so there is no save button; "close", or a click on the board around the sheet, closes it. The sheet holds the project, the description and, right under it, the activity log with its comments and the box to add one; then the plan, the open questions and your answers, the assignee and lane, labels, the checklist, links (parent and blocks) and "archive". Fields only the agent fills stay out of the way until they hold something: the plan and open questions appear once the agent writes them, your answers whenever there are questions, and an empty checklist shows only on a new card or one in todo, where you may add items yourself. Cards are never deleted, only archived. The log leaves out what the dots, the session button and the pull request link already show, and an agent taking or dropping a card itself.
  • A card the agent has worked shows "session" and the start of its id under the title: click it to copy claude --resume <id>, which reopens that run's Claude Code session in a terminal. A card that landed by pull request also links to it there.
  • An agent's comment has a "claude's output" box under it, closed: open it to read the whole run as you would have seen it in the terminal — every file it read, every command it ran, and what it cost.
  • A card in verify also has a "move to done" button in its sheet, next to "close": the one click that ends the card.
  • Ctrl- (or ⌘-) click toggles a card in the selection; shift-click takes the whole run from there to the card, as long as both are in the same lane. Dragging one card of a selection moves all of them; dragging an unselected card moves it alone. A plain click clears the selection and opens the card, and Esc clears it.
  • The done lane has "archive all" for every done card the board shows; one card is archived from its sheet.

Signals

A card leads with up to three dots, on the board and in its sheet. Each shows only while it is lit; a card with none of them has no dot.

  • green dot: it pulses while an agent is working on the card. The project tabs above the board say the same per project: a tab's color dot pulses while an agent works on any card in that project, so you see it even under another tab, and the "All" tab shows a grey dot that pulses while an agent is working on anything.
  • blue dot: the card's branch is merged into the project's base branch: lit by the agent after the land and deploy once git shows the branch merged, or, for a pull request, by the next run once the PR is merged. purple dot: it is deployed to the local test backend or a device, lit by the agent's deployed: comment. Moving the card back to plan, develop or test clears them.
  • red stripe down a card's left edge, with a "blocked by #12" pill: the card is blocked, it can't start until those cards reach verify (a blocker with an open pull request: once it is merged) or done. In a project that lands by pull request, a blocker in verify counts only once its pull request is merged: one dragged back to verify by hand without a new one (rework clears the old one) still blocks, and so does a person's task card there, so move that to done. Moving a blocker back out of verify blocks again: the link is never removed. amber stripe, with a "blocks #37" pill: other cards wait for this one. A card that is both has a half red, half amber stripe and both pills. The other card can be in another project. A link from a finished blocker or to a done card no longer counts, and done cards are never marked; the marks update by themselves when a blocker moves to verify or done.
  • ⟶ arrows go from a blocking card to the cards it blocks, across lanes or within one; one that skips a lane goes round the cards there, never under them. They are faint so a busy board stays readable: hover a card to light its arrows, both ways. An arrow shows only when the board shows both cards; one in another project's tab, archived or done has just the pill. Arrows never get in the way: clicks and drags go through to the card below.
  • status bar, at the bottom: which agent is working on which card, doing what, and since when. Click a card in it to open it.

4. The agent

Nothing works the board by itself. You start the work by hand: open a Claude Code session in the project's folder and run /tickets-start: it works the board every 15 minutes while that session is open (/tickets-start once for one run, /tickets-start 12 for card 12 only). A tick with nothing to do costs no tokens: a hook that /tickets-start installs answers it with tickets: nothing to do (<time>) before the model wakes, and lets it through when a card is ready, the board is down or the folder has no project. If the board is down it starts it, and if the session has no board tools (Claude Code connects them only when a session starts, so a session opened before the board has none until /mcp reconnects) it works over the board's web API instead. /tickets-start can start the board when you log in, so that rarely happens. It works every ready card of that project in plan, develop and test through to verify, and writes what it does onto the board as claude-agent: the plan, comments, the moves, and a new idea card for any follow-up it finds. Cards in "No Project" are never worked. It works up to 3 cards at once, but only one in test at a time. A card in plan gets one background agent that writes the plan, posts it with its checklist and, unless the plan has open questions, moves the card to develop and builds it in the same go, so the code is read once. A card already in develop, and every card in test, gets a new agent with a clean context, so the test reviews work it did not write. The planning agent runs on your session's model, since planning is judgement, and so does the build it goes on to; the agents that build a card already in develop, review it in test and deploy it run on the cheaper Sonnet. Each agent is handed the whole card: its description, plan, answers, checklist and comments, and the project's rules. Tests, the deploy and the merge into the base branch go one card after another. The status bar shows the card it started last and how many are in flight. A card that passes its tests is pushed as card/<id> and then lands the project's way: merged locally into the base branch, or opened as a pull request with gh, whose merge the next run notices and marks with the blue dot. Moving a card from todo, verify or done back to plan, develop or test drops its pull request link, and its next ship opens a new pull request, or picks up the branch's PR again if that one is still open: a closed or merged one is never reused.

You can still move a card while the agent works it: a person's move wins. The agent then posts its output as a comment saying the card was moved during the run and leaves it where you put it. A card assigned to a person is never taken.

Blocked by a person. When a stage needs something only you can do (a credential, an account, a service to enable, a device to plug in), the agent opens a todo card for each such task, links it as blocking the card, and comments the new cards' numbers. The card stays in its lane, marked blocked, and runs skip it until those cards reach verify (one with an open pull request: once it is merged) or done.

5. How you work with it

  1. Create a project under "projects…". Point its path at a git repo, put its test and deploy rules in the repo's CLAUDE.md and anything board-specific in its agent instructions. Whatever you leave out shows up as a card in todo telling you what is still missing. Or let /tickets-start do it: run in a Claude Code session in the repo's folder, it starts the board if it is down (and offers to start it at every logon), registers the MCP server, installs the idle gate, helps write the CLAUDE.md rules and creates the project, fixing only what is missing. Then it works the board every 15 minutes (or /tickets-start 10m) for as long as that session stays open, and ends with a link to the board; /tickets-stop stops it. /tickets-open-board opens the board in your browser any time.
  2. New Card in todo: a title and a clear description of what you want and why.
  3. Drag it to plan, and the next run of /tickets-start takes it. Watch the status bar and the comments. The plan's steps become the card's checklist and the agent ticks each one as it finishes it, so the checklist (and the ☑ done/total chip on the board card) is its live task list.
  4. Open questions in the plan? Fill in "your answers": the next run replans with them. A question that comes with options shows them as radio buttons under the questions, the agent's pick marked "recommended": a click writes N. <option> into your answers, and you can still type there.
  5. In verify: read the comments, look at the branch, try the deployed build. With "merge into the base branch" the agent has already merged card/<id> and pushed the base: the deploy comment says so, or why it skipped the merge (the repo was on another branch or had uncommitted changes) or that it conflicted; only then merge it yourself (unless the project's deploy instructions merged it; the blue dot shows it is on the base). With "open a pull request", merge the PR linked under the title. Then click "move to done".
  • Not what you asked for? Rewrite the description, move the card back to plan; the next run takes it again.
  • Keep one concern per card, keep project instructions current, use links for dependencies, and archive what you no longer need.

6. Other agents over MCP

Any MCP client can use the board at http://127.0.0.1:8123/mcp. The tools: list_cards, get_card, create_card, update_card, comment, link_cards, unlink_cards, create_user, list_projects and set_activity.

  • Every write passes actor, the caller's name, so the log says who did what.
  • Plans go in plan, never over the person's description.

7. Limits

  • No auth and no multiple users. No remote access beyond your own LAN, and that one without a password.
  • No live push: the board checks every few seconds and refreshes itself when anything changes.
  • No search and no attachments.
  • Cards are never deleted, only archived.
